Adapt OnIt's safeguards onto Fweddie

Fweddie now runs OnIt's own safeguard stack by spawning OnIt's real stdio
MCP servers and talking to them over the protocol, instead of re-implementing
anything. Three layers, all enforced inside the spawned server process:

1. AST command allowlist (command_policy.py) - fail-closed parser; every
   executable must be allowlisted, installs gated + version-pinned. Pinned on
   with ONIT_COMMAND_ALLOWLIST=1 (off by default on a host).
2. DATA_PATH file jail - read/write/edit/serve/grep confined to MCP_DATA_PATH.
3. Human-in-the-loop approval (approvals.py) - a command the allowlist will not
   decide alone returns a needs_approval ticket; the new mcp_bridge.Guard is the
   harness side: it shows a person the command and re-issues the call carrying
   the single-use ticket (approval_token + approval_scope). Refusals are
   remembered per session. Fail-closed: no answer in MCP_APPROVAL_TIMEOUT = deny.

mcp_bridge sets ONIT_APPROVAL_CHANNEL=1 so ASK becomes a ticket (else every ask
collapses to a hard deny). The approval params are harness-filled - the model
never sees them and the server overwrites them on every call.

Verified end-to-end against the real OnIt server: an allowlisted command runs,
an unlisted one (lscpu) returns a ticket the Guard redeems, and a never-ask
privilege-escalation command is a hard deny. test_guard.py covers the Guard
logic with a stubbed tool call.

Files: mcp_bridge.py (bridge + Guard), config.py (approval knobs + prompt),
agent.py (wire the Guard), test_guard.py, Fweddie-notes.md (section 7).
