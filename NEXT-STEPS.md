## 1. Task 1 — tool use must be spoken, and must cover OnIt's full toolset

### 1.1 Current behaviour, precisely

The wiring is: `llm -> tts -> output -> assistant_agg`. A tool call is generated by
the LLM, executed by `mcp_bridge.ToolBridgeProcessor._make_tool`'s handler, and the
handler's `str` return goes back to Pipecat, which appends it to the LLM context and
re-invokes the LLM. The LLM's *second* reply is what reaches the TTS.

So the design intends speech after a tool call. The log says it does not happen.
Three candidate causes, to be separated by experiment rather than assumed:

| #  | Hypothesis                                    | How it is tested          |
|----|-----------------------------------------------|---------------------------|
| H1 | The second LLM call returns empty `content`   | log the raw completion    |
|    |                                               | for a tool turn           |
| H2 | The result is so large the model stalls or    | replay with the result    |
|    | the turn is cut                               | truncated                 |
| H3 | The turn is torn down before the second       | watch the frame trace for |
|    | reply (barge-in / turn-stop)                  | `EndFrame` vs             |
|    |                                               | `InterruptionFrame`       |

H2 is the leading candidate: the successful call returned 602 chars of JSON with
URLs and full article text, and `TOOLS_SYSTEM_PROMPT` asks for "one or two short
spoken sentences" — a model handed 600 chars of JSON often answers with nothing
parseable. H1 is next: `LLM_THINKING` is off, and the configured model
(`gemma4:31b-cloud`) may emit its answer in a reasoning field, which is exactly the
bug already documented for Qwen3.8 in §2 of the handover.

### 1.1a DONE — the real cause, found by experiment

All three hypotheses above were wrong, and so was the design statement they
rest on. The handler's return value does **not** go back to Pipecat:

```python
# pipecat/services/llm_service.py, _run_function_call
await item.handler(params)      # return value discarded
```

`FunctionCallParams.result_callback` is the only way a direct function can
deliver a result — its docstring says so: *"Callback to deliver the result of
the function call."* Our handler returned a string and never called it, so no
`FunctionCallResultFrame` was ever broadcast. The assistant aggregator never
appended the tool message, the LLM was never re-invoked, and the turn ended at
the tool result. **The tool worked; only the reply was lost.**

How each hypothesis was tested and refuted:

| #  | Test                                           | Result         |
|----|------------------------------------------------|----------------|
| H2 | Replay the turn at the model: 602 chars, then   | **Refuted.**   |
|    | 300. Same question, real tool result            | The model      |
|    |                                                | answers fine   |
|    |                                                | at both sizes: |
|    |                                                | 152 and 120    |
|    |                                                | chars spoken   |
| H1 | Same replay; inspect `content`, `finish_reason` | **Refuted.**   |
|    |                                                | `stop`, and    |
|    |                                                | content is     |
|    |                                                | non-empty      |
| H4 | Same replay with the tools still offered, which | Refuted; the   |
|    | is what the pipeline actually does             | model still    |
|    |                                                | speaks         |
| H3 | Frame trace with probes either side of the TTS  | **Refuted.**   |
|    |                                                | No             |
|    |                                                | interruption;  |
|    |                                                | the frame      |
|    |                                                | never existed  |

The decisive evidence: on the broken build the aggregator logged
`FunctionCallsStartedFrame` and `FunctionCallInProgressFrame` but **never**
`FunctionCallResultFrame`. After the fix the same run logs all three, and
`bot_text` follows.

### 1.2 The fix, in three layers

**Layer 1 — make the tool turn observable.** Add a `tool_turn` event to the bus
carrying: the tool name, the result length, the *raw* second completion, its finish
reason, and whether `content` was empty. Nothing can be fixed until H1/H2/H3 are
told apart, and the current event log cannot tell them apart — it records the result
but not what the model did with it.

**Layer 2 — speak the result deterministically.** Do not rely on the model choosing
to talk. After a tool completes, emit a short spoken acknowledgement *and* the
answer, both as `TTSSpeakFrame` pushed downstream from the bridge:

- before the call: "Checking the weather." / "Searching for that."
- on refusal or error: say plainly what was refused or failed, and why — the
  `TOOLS_SYSTEM_PROMPT` already requires this in words, but nothing enforces it
- on success: the model's sentence, falling back to a bounded summary if `content`
  came back empty

`TTSSpeakFrame` exists in Pipecat 1.15.0 and is the supported way to speak a fixed
utterance without going through the LLM. This is what makes the guarantee real.

**Layer 3 — bound what the model is asked to swallow.** Cap the tool result handed
back to the LLM (a few hundred chars, head plus a "[truncated, N chars]" marker) and
keep the full result in the session folder (§5) for the dashboard to show. This
addresses H2 and keeps a 602-char JSON blob from being the thing that decides whether
the agent speaks.

### 1.3 Dashboard: tool output is written, not spoken

The requirement is that tool output appears **on the dashboard**. It already does,
as two `st.caption` lines (`dashboard.py` ~204–215), which is the weakest possible
presentation: a grey one-liner, truncated at 200/300 chars, with no way to expand.

Target: a collapsible **tool card** per call, showing name, arguments, duration,
status (ok / refused / error), and the full result in a scrollable block with a copy
button. This is also where a truncated model-visible result and the full stored
result visibly differ, which makes §1.2 Layer 3 honest rather than hidden.

### 1.4 Proving parity (so it cannot drift silently)

Add `test_tool_parity.py`: enumerate the tool names OnIt's servers advertise over
MCP, compare to a checked-in expected list of 14, and fail on any difference. Run it
in CI and at agent start-up (log-only at start-up, failing in the test). Without
this, a future OnIt release that adds a tool would silently leave WanDog behind —
which is the actual risk behind "make sure it can use the same tools".

### 2.2 Files

| File | Tracked? | Purpose |
|---|---|---|
| `secrets.example.yaml` | **yes** | committed template, placeholders only, never a real value |
| `secrets.yaml` | **no** | the file you edit; added to `.gitignore` |
| `.gitignore` | yes | gains `secrets.yaml` and `secrets.*.yaml` |

`secrets.example.yaml` is a YAML file with one key per row above, each value the
empty string, each preceded by a comment saying which tool breaks without it and
where to get it. Copy it, fill it in, done:

```bash
cp secrets.example.yaml secrets.yaml
```

### 2.3 Loading it, without weakening what already works

`config.resolve_llm_api_key()` currently resolves in this order: env var → OS
keychain → `~/.onit/secrets.yaml` → `OPENAI_API_KEY`. The new file must slot in
**without breaking the keychain path**, because that is how the working setup
authenticates today (the handover is explicit: "no `export` needed, the key is in the
OS keychain").

Proposed order, first hit wins:

1. `ONIT_LLM_API_KEY` (unchanged)
2. OS keychain (unchanged)
3. **`./secrets.yaml` (new)** — repo-local, per-project override
4. `~/.onit/secrets.yaml` (unchanged)
5. `OPENAI_API_KEY` (unchanged)

Placing it at step 3 means the repo file can override a stale global key, while a
machine that never creates the file behaves exactly as it does now. That is the
property to preserve: **the file is additive, and its absence changes nothing.**

For the *tools*, the keys must reach the spawned MCP subprocesses. `mcp_bridge`'s
`_params()` already builds `spawn_env` from `os.environ` plus the pinned OnIt knobs;
the loader therefore exports the tool keys into `os.environ` at start-up, before any
server is spawned. This is the one place a process-wide side effect is correct,
because the servers are separate processes with no config of their own.

### 2.4 Hygiene

- `secrets.yaml` is created `chmod 600`, matching OnIt's own `_file_store_secret`.
- The loader logs **which keys are present, never their values** — a set of names,
  so a missing `TAVILY_API_KEY` is visible in the log without a secret being.
- `secrets.yaml` must also be excluded from the agent's own `read_file` jail. This
  matters: the file jail root is `/tmp/onit/data`, but `bash` runs as you and can read
  the repo. §2.5 covers the mitigation.

### 2.5 One risk worth stating plainly

A voice agent whose `bash` tool runs as your user can read `secrets.yaml` — either
directly or by the model being asked to. The template will carry a comment saying so,
and the recommended default is to keep only *low-value* keys in the repo file
(benchmark judge keys, Tavily, OpenWeather) and leave high-value ones (GitHub PAT)
in the keychain, which the file never needs to duplicate. This is a design decision
to make explicitly, not a detail to discover later.

### 2.6 Acceptance criteria

- A fresh clone with no `secrets.yaml` starts exactly as it does today.
- `cp secrets.example.yaml secrets.yaml`, fill in one tool key, and that tool works.
- `git status` never lists `secrets.yaml`; `git check-ignore` confirms it.
- `get_weather` stops returning "API key not set" once its key is present.

### 3.2 The adapter is the real work

`fd-benchmark` starts the assistant with a benchmark transport instead of a mic and
speaker. `adapters/assistant_entry_template.py` has three fill-ins, and WanDog
already satisfies the hard one:

```python
PROJECT_MARKER = "agent.py"

def audio_rates() -> tuple[int, int]:
    return 16000, 16000          # fdbench requires 16 kHz in

async def build(transport, log_dir):
    # return (run_coroutine, async_cancel)
```

`agent.build_pipeline()` already accepts `transports=` and returns
`(pipeline, task, input, output)`. That hook exists for exactly this purpose, and it
is **already exercised**: `test_endtoend_answer.py` line 110 passes
`transports=(FakeTransport(), FakeTransport())` to drive the real pipeline from a wav
file. So the adapter is a proven pattern, not an untested guess — it calls
`build_pipeline` with the fdbench transport injected, and the pipeline under test is
the real one, not a mock. `FakeTransport` in that test is also the shape to copy: a
`FrameProcessor` that forwards every frame and never produces audio.

One detail to get right: `build_pipeline` computes `proc_rate` from
`config.ASR_SAMPLE_RATE` and constructs the Silero VAD at that rate. The benchmark
feeds 16 kHz, so the resampler must be a no-op or be bypassed for the injected
transport; otherwise VAD sees the wrong rate and scores every clip as silence. This
is the most likely first-run failure and belongs in the plan, not in a debugging
session at 2 a.m.

## 4. Task 4 — a dashboard that looks like a modern agent UI

### 4.1 What exists

A Streamlit page that tails a JSONL log, renders events as chat messages, and
offers one sidebar toggle for the mic. It refreshes with `@st.fragment(run_every=1.0)`.
There is **no text input path at all**, and the mic control is a labelled toggle, not
an icon.

Two constraints follow from that and shape the whole task:

1. **The agent is the only process with a pipeline.** The dashboard is a separate
   process that can only communicate through files. So every new control — typed
   text, stop, upload — must be a file the agent polls, exactly as
   `MicControlWatcher` already does for the mic. This is the existing pattern and
   the cheapest correct one.
2. **A `run_every` fragment cannot host a text input.** A widget inside an
   auto-refreshing fragment is re-rendered every second and loses focus mid-typing.
   The composer must live *outside* the refreshing fragment; only the transcript
   refreshes.

### 4.2 Layout — ChatGPT-like, which is what was asked for

```
+-------------------------------------------------------------+
|  WanDog                                      [session info]|
|                                                              |
|   [ transcript, scrolls, auto-refreshing ]                   |
|                                                              |
|                                                              |
|  +--------------------------------------------------------+  |
|  | Type a message…                            [🎤] [➤]    |  |
|  +--------------------------------------------------------+  |
|                                                              |
+-------------------------------------------------------------+
```

- Composer pinned to the bottom, full width, centred with a max-width — the modern
  convention.
- **Mic icon on the left of the send button**: a mic glyph, **blue when active**,
  black/white when inactive. Implemented as an icon-only button whose colour comes
  from state, not from a toggle's chrome.
- **Send button** as an icon (arrow / paper-plane), which becomes a **stop** (square)
  while a turn is in progress — one control, two states, in the position a user
  already reaches for.

### 4.3 The three new controls, and how each reaches the pipeline

**Mic toggle — restyle only.** The mechanism already works: the dashboard writes
`<log>.mic_control.json` with `{"enabled": bool}`, and `MicControlWatcher` polls it
and pushes `STTMuteFrame` upstream. Replace the sidebar toggle with an icon button
and keep the file protocol untouched. **Do not rebuild what works.**

**Typed text — a new path into the same turn machinery.**
The dashboard appends `{"text": "...", "ts": ...}` to `<log>.text_input.json`. A new
`TextInputWatcher` processor, placed **immediately before `user_agg`**, polls that
file and pushes a `TranscriptionFrame(text=..., user_id="dashboard", timestamp=...)`
downstream. `TranscriptionFrame` exists in Pipecat 1.15.0 with exactly those
required fields. Because the frame enters where the ASR's final transcript would
have entered, typed text flows through the *same* aggregator, the same context, and
the same barge-in logic as speech. That is the whole reason to do it this way rather
than inventing a parallel path.

Typed turns must also emit `user_text` on the bus, so the transcript shows them
identically to spoken ones.

**Stop button — a real interruption, not a mute.**
The dashboard writes `<log>.stop.json`; a watcher pushes an `InterruptionFrame`
downstream. `InterruptionFrame` is the frame Pipecat's own barge-in uses to stop TTS
and cancel the in-flight response, so the stop button becomes barge-in by button
rather than by voice — which is precisely the analogy asked for. The send/stop swap
is driven by a `turn_active` state the agent emits on the bus: `bot_started` → stop
icon, `bot_stopped` → send icon.

### 4.4 Why not just use `st.chat_input`

Worth stating, because it is the obvious approach. `st.chat_input` is the natural
composer, and it renders as a modern input bar for free — but it cannot satisfy the
layout requirement on its own: it owns the whole row, so the mic icon and the
send/stop swap cannot be placed beside it, and the button cannot change from send to
stop while a turn runs. That is a layout constraint, not a bug in Streamlit.

The decision to make in phase 4a is therefore: **`st.chat_input` plus a separate
control row** (simple, slightly less unified) **versus `st.text_input` + two
`st.button`s in columns** (exactly the requested layout, a little more code). The
recommendation is the second, because the send/stop swap in the *same position* is
the specific behaviour asked for. Either way the composer must live **outside** the
auto-refreshing fragment, or it re-renders every second and loses focus mid-typing.

This is a layout decision to confirm during 4a by building both, not an assumption
to lock in now.

### 4.5 Phases

## 5. Task 5 — file upload, session folder, and source-of-truth confirmation

**Plan only, by request. Nothing here is to be built in this pass.**

### 5.1 Session folder

Today the file jail is a single flat root, `/tmp/onit/data` (`MCP_DATA_PATH`), shared
by everything. The proposal is one folder per conversation:

```
/tmp/onit/data/sessions/<session-id>/
    uploads/       files the user sent
    created/       files the agent wrote
    tool-results/  full tool output, when §1.2 caps what the model sees
    meta.json      session id, start time, model, and the mode flag below
```

`session-id` is generated at `session_start` and emitted on the bus, so the dashboard
can show the folder and the log can name it. The jail root is unchanged; only the
working subdirectory moves. That keeps the existing `ONIT_DATA_PATH` validation
intact — a session folder is *inside* the jail, not a new jail.

### 5.2 Upload path

Streamlit's `st.file_uploader` writes the file into the dashboard process's memory,
so it must be handed to the agent the same way every other control is: the dashboard
writes the bytes to `<log>.upload.json` (path + declared name + size), and the agent
copies them into `uploads/` under a sanitised name, rejecting path traversal, size
over a cap, and any type outside an allowlist. The copy, not the original name, is
what the tools see.

An upload is not a silent ingestion. It is a question.

### 5.3 The confirmation gate — the core of the requirement

> verify if the user wants to only use that file as a source of truth and say when a
> piece of information is not there, or if they would like to expand the search.

So an upload triggers a **spoken question**, not an action:

> "I've got `report.pdf`. Should I answer only from this file, or may I also search
> the web and your other documents?"

The answer sets a per-session mode, persisted in `meta.json`:

| Mode       | Behaviour                        | When info is missing    |
|------------|----------------------------------|-------------------------|
| `strict`   | only the uploaded file(s)        | say plainly it is not   |
|            |                                  | in the file — **do not**|
|            |                                  | go looking              |
| `expanded` | file first, then web + local     | say where it found it,  |
|            | corpus                           | and that it came from   |
|            |                                  | outside the file        |

Three properties this must have to be honest:

1. **The mode is visible.** The dashboard shows a banner — "answering only from
   `report.pdf`" — so the user is never in doubt which mode is live.
2. **`strict` failures are explicit.** Not a generic "I don't know", but "that isn't
   in `report.pdf`" — the requirement says *say when a piece of information is not
   there*.
3. **Mode changes are spoken and recorded.** Switching mid-session is allowed and
   must be confirmed, because silently widening the search would break the promise
   the strict mode made.

Mechanically, `strict` is a system-prompt constraint plus a tool filter: `search`
and `local_search` are not offered while strict mode is on, so the model cannot
route around the promise even if it wants to. That is stronger than asking it
nicely, and matches how the project already handles refusals — enforce in the
harness, not in the prompt alone.

### 5.4 Open questions to settle before building

- Does an upload end the current turn, or join the context mid-conversation?
- Multiple files: one mode for the session, or per file?
- Should `strict` mode still allow `read_file` on the session folder only? (Yes,
  recommended — the file itself must be readable.)
- Retention: does a session folder survive a restart, and for how long?

### 5.5 Acceptance criteria (for when it is built)

- An uploaded file lands in `sessions/<id>/uploads/` and is readable by `read_file`.
- The agent asks the strict/expanded question before answering anything about it.
- In `strict`, a question the file cannot answer produces "that isn't in the file",
  and no web search is attempted — verifiable in the event log by the absence of a
  `tool_call`.
- The dashboard shows the active mode for the whole session.
